Account opening for a Nordic savings and investment platform that launches in a second country without forking the code. Sweden and Denmark use one onboarding flow, and everything that is different between them lives in a market module: one folder of plain Java per country.

Chapter 1

Data flow

One Danish application, end to end

This chapter follows one Danish account application from the click in the browser to the server's answer and back. Sweden takes exactly the same path through the same code. Only the market's data and its ID-number rule are different.

Four kinds of API call make up the journey. The browser checks what it can, for speed. The server checks everything again at the end, because anyone can skip the browser and send requests to the server directly.

Chapter 1 · Data flow
Nordic Onboarding · A technical guide Chapter 1 · Data flow

The four calls

  1. Load Denmark: GET /api/markets, then GET /api/markets/DK/onboarding
  2. Verify identity: POST /api/markets/DK/identity/sessions
  3. Check the CPR number: POST /api/markets/DK/national-id/check
  4. Open the account: POST /api/markets/DK/applications

The market code is part of every URL, so every market uses the same endpoints and the same controller. For Sweden, the same four calls use SE instead of DK: GET /api/markets/SE/onboarding, and so on. The same code handles them, and MarketRegistry hands it Sweden's rules instead of Denmark's. There is no Sweden-only or Denmark-only endpoint.

What the answers mean

200 OK
The data that was asked for: the markets, a market's configuration, an ID check.
201 Created
The application was accepted.
422 Unprocessable
The application was rejected. The body lists the reasons, in the order of the flow.
404 Not Found
The market is switched off, or doesn't exist. Both look exactly the same.

A 404 is a standard problem detail (RFC 9457), from the live demo:

{ "title": "Not Found", "status": 404, "detail": "Market not available: NO",
  "instance": "/api/markets/NO/onboarding" }
A rejected application answers 422, not an error. A rejection is a normal outcome, so its body is ordinary data that the browser shows as a list, with a link from each reason back to the step that fixes it.

Loading Denmark: the screens come from configuration

The browser loads the Angular app from the same server, or from the service worker's cache on a repeat visit. The service worker is a small script the browser installs for this site. It keeps a copy of the app's files on the person's device, but never the API's answers.

The app asks which markets are live with GET /api/markets, and draws the Sweden/Denmark switch from the answer. A link ending in #dk picks Denmark, and GET /api/markets/DK/onboarding returns the whole flow as data:

When the market can't be loaded

"Couldn't reach the server. Check your connection and try again." The server didn't answer at all: no internet, or the server is down.
"This market isn't available right now." The server answered 404, because the market was switched off after the page loaded.

Choosing another market clears the message and shows that market.

Step 1

Verify identity, with simulated MitID

"Continue with MitID" sends POST /api/markets/DK/identity/sessions. Session here means an eID login session on the server, not a browser session or a cookie, and this call is the identity check, simulated. In a real system the person would sign in at MitID, and MitID would send back a signed proof for the server to verify. Here, the call pretends that succeeded.

The server creates a session id, remembers in memory that it belongs to Denmark, records a VERIFIED event, and answers: 

{ "sessionId": "sim-mitid-ccebc1b9-2b1a-4a9e-9407-abe52dfb0fd9" }

What the id is for

It is the proof of login. The browser keeps it in memory and sends it with the application. The server then checks that it exists and belongs to Denmark, and deletes it once an application is accepted, so one login can only be used for one application.

Why it can disappear

It lives in the server's memory. A restart or a new release forgets it, and the person is asked to log in again. That is also why the service runs one instance.

Step 2

The CPR number is checked twice

In the browser, the format pattern from the configuration is checked on every keystroke, for instant feedback. Only when the field holds a complete number in the right format, and 350 ms after the last keystroke, does the browser ask the server. It doesn't wait for the person to leave the field. A new keystroke cancels a check that is still waiting, and the same number is never sent twice.

On the server, Denmark's CprRule reads the number: the format, the century from the 7th digit, a real date, and not a date in the future. It deliberately has no modulus-11 check, an old checksum for CPR numbers. Denmark stopped guaranteeing it in 2007, so the check would reject real people.

Then comes the shared rule, written once for every market: the person must be at least 18 on today's date in Copenhagen. 

{ "valid": false,
  "message": "You must be at least 18 to open an account yourself." }

Each rejection records an ID_REJECTED event with a reason code, such as ID_UNDER_AGE.

Where to look: CprRule.java

Steps 3 and 4

Account type and confirmations

The account type is chosen in the browser, from the configuration: Aktiesparekonto or Depot. No call is needed, because the configuration already holds both, with this year's deposit cap.

Aktiesparekonto adds two confirmations, marked For this account: "I don't already hold an Aktiesparekonto with another bank" and "I am fully tax liable to Denmark". Switching account type drops confirmations that no longer apply, and Continue stays disabled until every required one is ticked.

Which confirmations a market asks for, and which ones belong to a single account type, is data in the market module. The confirmation screen has no Danish code.

On the server

The request passes through layers that each have one job. The controller only speaks HTTP. OnboardingService holds the rules every market shares. MarketRegistry turns DK into Denmark's market module, or answers 404 if Denmark is switched off. The market module supplies Denmark's data and its ID rule.

Where to look: OnboardingService.java

The checks, in the order of the flow

  1. The identity session exists and belongs to Denmark.
  2. The CPR number is valid, and the person is at least 18.
  3. A full name is given.
  4. The email address is valid.
  5. The account type is offered in Denmark.
  6. Every confirmation required for that account type is accepted.

Events: SUBMITTED, then either ACCEPTED, or REJECTED with the first failed check as its reason.

What this path never does

Stores nothing

There is no database. The login session lives only in the server's memory.

Logs no personal data

Events carry codes only: market, step, outcome, reason. Anything that looks like an ID number is masked in every log line.

Caches no API answer

The service worker keeps the app itself, never market configuration, so a switched-off market can't be shown from a cache.

What this does not catch: duplicates. The same person can log in again and apply again. With no database, nothing remembers earlier applications, and "one Aktiesparekonto per person" is only a confirmation the person ticks. A real system would check its customer records.

Design decisions

Why check the ID number on the server if the browser already checks it?
The browser only checks the format, for speed. The real rule needs today's date and the shared age policy, and any client can skip the browser's checks entirely, for example with curl.
Why answer a rejected application with 422 instead of an error?
A rejection is a normal outcome, not a failure. The body carries the field errors, so the browser treats them as data and links each one to its step.
Why is the market code in the URL?
One controller serves every market. The registry turns the code into a market, or into a 404 if that market is switched off.
What happens if Denmark is switched off in the middle of an application?
Every later Danish call answers 404. If the next one is the submit, the browser shows "Something went wrong. Please try again." The login session is gone too, because switching a market off starts a new revision of the service with empty memory.

Chapter 2

Architecture

The layers, and why each boundary exists

The code is split so that adding a market never means changing the shared code. The browser only renders what the server's configuration describes. On the server, every dependency points towards the domain: the shared rules in plain Java, which depend on nothing but Java itself.

Each country is a plug-in that implements one interface. Tests fail the build if a boundary is crossed: if the domain or a market imports a framework, if one market uses another, or if a market breaks the contract every market must follow.

Chapter 2 · Architecture
Nordic Onboarding · A technical guide Chapter 2 · Architecture

Where each piece runs

Everything is deployed as one container on Cloud Run: one Java process, whose jar holds the Java backend and the built Angular files. The Angular app is stored there, but runs in the visitor's browser once downloaded.

One "Open account" click, hop by hop

1 · Browser → Google

HTTPS over the internet: POST /api/markets/DK/applications, with a JSON body.

2 · Google → container

Plain HTTP on port 8080, inside Google's network.

3 · Tomcat → controller

Spring matches the POST and the URL to MarketController.submit, and Jackson turns the JSON body into a Java object, ApplicationRequest.

4 · controller → service

A plain Java method call in the same process: OnboardingService.submit.

5 · service → market

Plain method calls to MarketRegistry, DenmarkMarket and CprRule.

6 · back

The result becomes JSON with 201 or 422, and travels back the same way.

What a market module is

One folder per country, such as markets/dk: DenmarkMarket holds Denmark's data and CprRule reads its ID numbers. It is a Java package compiled into the same jar, not a separate service.

On a laptop it's two processes

ng serve runs the Angular app on port 4200 and passes /api calls to Spring Boot on port 8080. In production, both are the one container.

The boundaries, and what guards each one

Browser and server

What passes between the two sides: JSON. The server sends a market's whole flow as configuration; the browser sends the application back.

Why: the Angular app has no country code, so a new market needs no frontend change.

web and domain

What passes between the two sides: plain method calls, such as submit(code, request). The web layer turns HTTP into calls, and results into status codes: 201, 422, 404.

Why: the rules are tested without starting a web server. Guard: MarketApiTest for the HTTP contract.

domain, markets and frameworks

What passes between the two sides: nothing. The domain imports only Java, and the markets only Java and the domain. Why: they stay simple to test and easy to move. Guard: two ArchUnit rules in ArchitectureTest.

domain and markets

What passes between the two sides: the Market interface. A market supplies data and parsing rules; the domain applies the shared policy. Guard: MarketContractTest, which every market must pass.

market and market

What passes between the two sides: nothing. Sweden and Denmark never use each other, so a change for one country can't break the other. Guard: a second ArchUnit rule.

domain and the outside world

What passes between the two sides: two small interfaces, called ports: a Clock for time and OnboardingEvents for what happened. Why: tests set "today" and read the events, and the domain never knows about logs. Guard: OnboardingServiceTest.

built and live

What passes between the two sides: the setting MARKETS_ENABLED. A market can be deployed and still be dark. Guard: MarketRegistryTest.

The contract every market implements

A market is one class that implements Market. Everything that differs between countries is a method here: the code, the language and currency, the time zone, the eID, how to read the ID number, the account types and the confirmations. 

public interface Market {
    String code();                    // "SE", "DK"
    String displayName();
    Locale locale();
    ZoneId zone();                    // where "today" is decided
    Currency currency();
    IdentityProvider identityProvider();
    NationalIdRule nationalIdRule();  // how to read this country's ID number
    List<AccountProduct> products();
    List<Disclosure> disclosures();

    default List<StepType> steps() { return List.of(IDENTITY, PERSONAL_DETAILS, ACCOUNT_TYPE,
                                                     DISCLOSURES, REVIEW); }
    default int minimumAge() { return 18; }
}

Two methods have defaults: the steps and the minimum age. A market changes them only if it needs to. The ID rule is a second, smaller interface: 

public interface NationalIdRule {
    String label();          // "Personnummer", "CPR number"
    String placeholder();    // "YYYYMMDD-NNNN", "DDMMYY-SSSS"
    String example();        // a well-known test number, never a real person's
    String formatPattern();  // a loose pattern for the browser; the server decides
    NationalIdResult parse(String raw, LocalDate today);
}
Markets supply data and parsing rules. They don't decide policy. A market says how to read its ID number and what its minimum age is. The check "is this person old enough?" is written once, in OnboardingService, and applies to every market.

A market module: rules are data

Denmark's module is DenmarkMarket and its ID rule, CprRule, side by side in markets/dk. Its account types are data. The deposit cap is a map from year to amount, not an if statement, so next year's cap is one more entry: 

new AccountProduct(AKTIESPAREKONTO, "Aktiesparekonto",
        "Returns taxed at 17% each year. One per person, with an annual deposit cap.",
        Map.of(2025, new BigDecimal("166200"), 2026, new BigDecimal("174200")), true),
new AccountProduct("depot", "Depot (frie midler)",
        "A standard investment account with no deposit cap. Returns are taxed as share income.",
        Map.of(), false)

Confirmations are data too, and some belong to one account type only:

Disclosure.required("terms", "I have read and accept the account terms and conditions."),
Disclosure.requiredFor(AKTIESPAREKONTO, "ask-tax-liable", "I am fully tax liable to Denmark."),
Disclosure.optional("news", "Send me occasional product news by email.")

The contract test every market must pass

MarketContractTest runs the same checks for every market in its list. Adding Norway to the list runs them all for Norway too:

  1. Codes are unique, two-letter country codes.
  2. The market has a time zone.
  3. The flow starts with identity and ends with review.
  4. It offers at least one account type, with unique ids.
  5. It requires the terms to be accepted.
  6. Confirmation ids are unique.
  7. Every confirmation that belongs to one account type names an account type that exists, so a typo can't silently drop it.
  8. The ID field is consistent: its example matches the pattern and is valid, and garbage is rejected.

Boundaries the build enforces

Three ArchUnit rules read the compiled classes on every build. If any is broken, the build fails before anything is deployed. 

/** Rule 1: the domain is plain Java. This also keeps it from knowing about any one market. */
static final ArchRule domainIsPlainJava = classes()
        .that().resideInAPackage("dev.krishnapriya.onboarding.domain..")
        .should().onlyDependOnClassesThat()
        .resideInAnyPackage("java..", "dev.krishnapriya.onboarding.domain..");

/** Rule 2: markets never use each other, so a change for one country cannot break another. */
static final ArchRule marketsAreIndependent = slices()
        .matching("dev.krishnapriya.onboarding.markets.(*)..")
        .should().notDependOnEachOther();

/** Rule 3: markets are plain Java too, using only Java and the domain. */
static final ArchRule marketsArePlainJava = classes()
        .that().resideInAPackage("dev.krishnapriya.onboarding.markets..")
        .should().onlyDependOnClassesThat().resideInAnyPackage(
                "java..", "dev.krishnapriya.onboarding.domain..", "dev.krishnapriya.onboarding.markets..");

Rule 1 does two jobs: Spring can't sneak into the domain, and neither can a market, because the market packages are outside it too.

Ports: time and events

The domain needs two things from the outside world: the current time, and somewhere to report what happened. It asks for both through small interfaces, called ports, and Spring plugs in the real ones at startup:

Time: an injected Clock

In production it is the system clock in UTC, and each market turns it into its own local date. In tests it is fixed, so "today" can be any date, including the minute before and after an 18th birthday at Copenhagen midnight.

Events: OnboardingEvents

In production, OnboardingLog writes each event as a JSON log line. In tests, a plain list collects them, so a test can check exactly which events an application produced. 

// OnboardingServiceTest: a fixed clock, and events collected in a list
Clock clock = Clock.fixed(instant, ZoneOffset.UTC);
MarketRegistry registry = new MarketRegistry(
        List.of(new SwedenMarket(), new DenmarkMarket()), Set.of("SE", "DK"));
private final List<OnboardingEvent> events = new ArrayList<>();
// ... new OnboardingService(registry, clock, events::add)

The web layer only speaks HTTP

MarketController turns each request into one call on OnboardingService, and the answer into a status code. It holds no rules: 

@PostMapping("/{code}/applications")
public ResponseEntity<ApplicationResult> submit(@PathVariable String code,
                                                @RequestBody ApplicationRequest request) {
    ApplicationResult result = onboarding.submit(code, request);
    return ResponseEntity
            .status(result.accepted() ? HttpStatus.CREATED : HttpStatus.UNPROCESSABLE_CONTENT)
            .body(result);
}

One error shape

ApiExceptionHandler turns an unknown or switched-off market into a 404 problem detail. A built but disabled market looks exactly like one that doesn't exist.

Synthetic traffic, kept out of the domain

SyntheticTrafficFilter spots the hourly test sign-up by a request header and tags its log lines. The domain never sees the header.

One place where Spring meets the domain

MarketWiring creates the markets, the registry, the clock, the event logger and the service. It is the only class that connects the plain-Java domain to Spring: 

@Bean Market sweden()  { return new SwedenMarket(); }
@Bean Market denmark() { return new DenmarkMarket(); }

@Bean MarketRegistry marketRegistry(List<Market> markets,
                                   @Value("${markets.enabled}") Set<String> enabled) {
    return new MarketRegistry(markets, enabled);
}
@Bean Clock clock() { return Clock.systemUTC(); }
@Bean OnboardingEvents onboardingEvents() { return new OnboardingLog(); }
Built is not the same as live. The registry receives every built market, but only enables the codes in MARKETS_ENABLED. It checks every built market for a duplicate code, so a clash fails the release that ships a market dark, not the later switch that launches it.

The frontend renders configuration

The Angular app is split the same way: one part holds state, the parts below it only show and emit, and none of them knows a country.

App shell app.ts
Loads the list of live markets, draws the Sweden/Denmark switch, loads the chosen market's configuration, and shows the error messages. Quick switching always ends on the last market clicked.
Flow onboarding-flow.ts
Holds the application's state, in Angular signals and one reactive form: the current step, the login session, the details, the chosen account and the ticked confirmations. It decides when Continue is allowed, calls the API, and resets everything when the market changes.
Steps steps/*.ts
The identity, details, account type and confirmation screens. Each one receives the configuration as an input and reports what the person did as an output. None of them calls the server.
Core core/*.ts
The types that mirror the server's JSON, small helpers such as formatting money in the market's locale, and MarketApi, the only code that sends HTTP requests.
No country code. The labels, the ID format, the account types, the caps and the confirmations all come from GET /api/markets/{code}/onboarding. The same components show Sweden and Denmark.

Installable as an app

The frontend is a progressive web app (PWA). A manifest gives it a name, icons and its own window, and a service worker keeps a copy of the app's files on the device, so it can start without a connection.

The one boundary the service worker keeps

It caches the app itself, but never an API answer. A cached market configuration could show a market that the kill switch has turned off. Requests to /api and /actuator always go to the server.

A frontend test checks these cache rules, and CI checks that the real container serves the manifest, the icons and the worker.

Design decisions

Why one service for every market, not one per market?
The flow and the shared rules are the same everywhere, so one service keeps them in one place. A service per market would copy them, and the copies would drift apart.
Why is a market a class, not a configuration file?
Most of a market is data, but reading an ID number is real logic: check digits, century rules, impossible dates. A class can hold both, and the contract test can call it.
Why can't markets use each other, even to share code?
So that a change for one country can't break another. Code that two markets truly share belongs in the domain, where every market can use it and the domain's tests cover it.
Why keep the domain free of Spring?
Its tests run as plain Java, in a fraction of a second, without starting anything. It also keeps the rules readable: what's in the domain is business logic, nothing else.
Why a registry instead of a switch on the market code?
Adding a market then means registering one more object. There is no list of countries in the shared code to update, and a dark market answers 404 like any unknown code.
Adding Norway, in short: a NorwayMarket and a FodselsnummerRule in markets/no, one bean in MarketWiring, one entry in MarketContractTest. Nothing in the domain, the web layer or the Angular app changes.

Chapter 3

Delivery

From git push to traffic on a new version

Every change goes through a pull request, and CI tests it in four jobs before it can reach main. When main is green, the deploy job releases it by itself: Google Cloud builds the image, starts a new version that gets no traffic, and the release smoke-tests that version at its own private address. Only then does it move all traffic.

The last release took 4 minutes from the merge to 100% of traffic. A broken build never reaches customers, and going back is one command.

Chapter 3 · Delivery
Nordic Onboarding · A technical guide Chapter 3 · Delivery

What CI checks

CI runs on every pull request, and again on main after the merge. A newer push to a branch cancels that branch's older run, but a run on main is never cancelled, because it may be in the middle of a release.

backend

mvn verify: 115 tests, including the ArchUnit rules, the market contract, the HTTP contract and the monitoring contract tests.

frontend

37 tests, then the production build.

container

Builds the real image and starts it. Then it checks that it passes the smoke test, runs as a non-root user, completes a synthetic sign-up in both markets, writes JSON logs with tagged events, can be installed as a PWA, and goes dark for a market that is switched off.

scripts

Tests the release and kill-switch scripts against a fake gcloud, so their logic is checked without touching Google Cloud.

deploy

Runs only on main, only after all four jobs pass, and only one at a time.

One image: Angular inside the Spring Boot jar

The Dockerfile builds the whole app in three stages, so the image that runs holds only a Java runtime and one jar:

  1. Frontend: Node 24 installs the exact packages from the lock file and runs the Angular production build.
  2. Backend: Maven builds the Spring Boot jar, with the Angular build copied in as its static files. Dependencies get their own layer, so a code change doesn't download them all again.
  3. Runtime: a Java 25 runtime and the jar, nothing else. The tests already ran in CI, so the image build skips them. 
# 3. Runtime: only a Java runtime and the jar
FROM eclipse-temurin:25-jre
COPY --from=api /api/target/onboarding-0.1.0.jar app.jar
ENV LOGGING_STRUCTURED_FORMAT_CONSOLE=dev.krishnapriya.onboarding.logging.CloudLoggingFormat
# Not root, so a compromised app can't modify the image or anything else it doesn't own.
USER 1000
# Java defaults to a quarter of the container's memory for its heap; small instances need more.
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75", "-jar", "/app/app.jar"]

Same origin, no CORS

Because the Angular files are served by the same Spring Boot app as the API, the browser calls /api/... on the same address. There is no second service and no cross-origin setup.

Only what's needed is uploaded

.gcloudignore keeps .git and everything in .gitignore out of the upload. .dockerignore is an allowlist: only the backend sources and the frontend reach the image build.

The release, step by step

scripts/deploy.sh does the release. The deploy job signs in to Google Cloud (Chapter 4 explains how) and runs it:

  1. Refuse an unsafe upload. If a credentials file would be uploaded with the source, the release stops before anything changes.
  2. Deploy with no traffic. gcloud run deploy --source . --no-traffic --tag=candidate builds the image in Google Cloud and starts a new revision. Customers can't reach it: it is only at its own tagged address.
  3. Smoke-test the candidate. The health check, the page and the API must all answer at that address. If not, the release fails and customers stay on the current revision.
  4. Move all traffic. The candidate gets 100%, and its tag is removed, so it isn't kept running once a later release replaces it.

The settings each release keeps

--min=1

One warm instance for the service, on whichever revision serves traffic, so the first visitor doesn't wait for Java to start.

--min-instances=default

No warm copy kept for each version. Otherwise every tested candidate would be kept running, and billed.

--max-instances=1

At most one running copy of each version, because the simulated eID sessions live in that copy's memory.

MARKETS_ENABLED

Not set by a release, on purpose. A release keeps the service's current value, so a market that was switched off stays off.

How we know it works

The release logic is tested

deploy.test.sh runs deploy.sh against a fake gcloud that records every call:

  • a passing candidate is tested at its tagged URL, then gets 100% of traffic
  • a failing candidate gets no traffic, and the release fails
  • a first-ever deploy creates the service directly
  • a release is refused if a credentials file would be uploaded

A real release, watched

During a real release, a script called the live API every 2 seconds for 3 minutes and got 86 successful answers out of 86. Customers saw no gap while traffic moved.

Going back is one command

gcloud run services update-traffic nordic-onboarding \
  --to-revisions=<previous>=100

No rebuild: the old revision is still there.

One release at a time. Releases and the kill switch share one queue, so they never change the service at the same moment.

Design decisions

Why test the new version at its own address instead of a staging environment?
The candidate runs the real image, on the real platform, with production's settings. A separate staging environment would cost more and could drift from production. Here the only difference is that customers can't reach it yet.
Why release automatically on every green main?
Small, frequent releases are easier to check and easier to undo. The pull request is where a person decides; after that, the pipeline and its tests decide.
Is the deployed image the same one CI tested?
Not byte for byte. CI's container job tests an image built from the same commit and the same Dockerfile, and Google Cloud builds the released image again from that source. A stricter setup would build the image once and promote that exact image.
Why not set MARKETS_ENABLED during a release?
A release and a market launch are separate decisions. If a release reset the setting, fixing a bug could quietly switch a market back on that was turned off for a reason.
What happens to a candidate that fails its smoke test?
It stays at 0% of traffic and the job fails, so the failure is visible in GitHub. Customers keep using the current revision, and the next release replaces the candidate.

Chapter 4

Cloud

What runs where in Google Cloud, and who is allowed to do what

The app runs on Cloud Run in europe-north1, in Finland. Google Cloud builds each release from source, stores the image, and collects the app's logs. GitHub signs in with short-lived tokens instead of stored keys, and only from this repository's main branch.

Three narrow identities do the work: one deploys, one builds the image, and the app itself runs as one with no permissions at all.

Nordic Onboarding · A technical guide Chapter 4 · Cloud

Signing in without keys

GitHub never holds a Google key. Each run proves who it is with a short-lived token, and Google decides whether that proof is good enough. This is called Workload Identity Federation.

  1. GitHub issues a token. The workflow has permission id-token: write, so GitHub gives it a token that says which repository and branch the run belongs to. It is short-lived.
  2. Google checks it. The token goes to the identity pool github and its provider nordic-onboarding, which only trust tokens from GitHub and only accept one repository on one branch.
  3. Google lends an identity. If the check passes, the run gets short-lived credentials for github-deployer, and only for that one.
  4. The credentials expire. Google's access lasts an hour at most, by default. There is no long-lived key to rotate or to leak.

The provider's real condition, read from Google Cloud:

assertion.repository == 'krishnapriya-venkatakrishnan/nordic-onboarding'
  && assertion.ref == 'refs/heads/main'

What a pull request can't do

A run for a pull request carries its own branch in the token, so the condition fails and it can't sign in. Only code that has been merged into main can deploy.

What the workflows that don't need Google get

Nothing. The hourly synthetic sign-up only calls the public URL, so it has no Google credentials at all.

Design decisions

Why Cloud Run?
It runs a container without servers to manage, gives every revision its own address, and splits traffic between revisions. That last part is what makes the no-traffic release in Chapter 3 possible.
Why europe-north1?
It is in Finland, close to Nordic customers, and keeps the service in the EU.
Why three identities instead of one?
Each one can only do its own job. The identity that runs on every request, the app's, has no permissions at all, so a bug in the app can't be turned into access to the cloud project.
Why not store a key in GitHub's secrets?
A key works until someone revokes it, from anywhere, for anyone who has a copy. The federated access lasts an hour at most, and only this repository's main branch can get it.
Why can't CI make the service public or change monitoring?
So a compromised workflow could at worst deploy code that still has to pass the smoke test. It couldn't open up access, or silence the alerts that would show something is wrong.
Why one warm instance, when Cloud Run can scale to zero?
A cold start means waiting for Java to start. One warm instance keeps the demo quick, and because the eID sessions live in memory, one copy of each version is also the maximum.

Chapter 5

Observability

From a log line to an alert email

Every outcome in the flow becomes one JSON log line, with codes only and every ID number masked. Cloud Logging counts those lines into a metric, and the metric feeds a dashboard and an alert that emails when Denmark rejects too many applications.

An uptime check watches the health endpoint from three continents, an hourly synthetic sign-up proves both markets still work, and a kill switch turns a market off in about a minute. Everything is defined as code in the repository.

Chapter 5 · Observability
Nordic Onboarding · A technical guide Chapter 5 · Observability

From an event to a log line

OnboardingService records an event at each outcome, through the OnboardingEvents port from Chapter 2. An event holds codes only:

VERIFIED
The eID login succeeded.
ID_REJECTED
An ID-number check failed while typing, with a reason such as ID_UNDER_AGE or ID_CHECK_DIGIT. One person can cause several.
SUBMITTED
"Open account" was pressed.
ACCEPTED
The application passed every check.
REJECTED
It didn't, with the first failed check as its reason.

OnboardingLog turns each event into one log line. In the container, the log format is JSON in the shape Cloud Logging reads: time, severity, logger and message, then the event's fields. Cloud Logging stores it like this (a real line from the rehearsal): 

{ "timestamp": "2026-10-17T15:21:22.954429030Z", "severity": "INFO",
  "jsonPayload": { "logger": "onboarding", "message": "DK REVIEW REJECTED ID_UNDER_AGE",
                   "market": "DK", "step": "REVIEW", "outcome": "REJECTED", "reason": "ID_UNDER_AGE" } }

No ID number reaches a log

Events can't carry one

They hold codes only. The request objects that do hold personal data print a toString() that leaves it out, so an error trace can't show it either.

And every line is masked anyway

As a second line of defence, the log format replaces anything shaped like a Swedish or Danish ID number with [national ID masked], in messages, fields and stack traces. It errs towards masking. 

// NationalIdMask: 6 or 8 digits, an optional - + or space, then 4 digits, not inside a longer number
Pattern.compile("(?<!\\d)(?:\\d{2})?\\d{6}[-+ ]?\\d{4}(?!\\d)")

From log lines to numbers

A log-based metric counts matching log lines, and turns chosen fields into labels that charts and alerts can filter and group by. The whole definition lives in infra/metrics/onboarding_events.json: 

"filter": "resource.type=\"cloud_run_revision\"
           AND resource.labels.service_name=\"nordic-onboarding\"
           AND jsonPayload.logger=\"onboarding\"",
"labelExtractors": {
  "market": "EXTRACT(jsonPayload.market)",   "step": "EXTRACT(jsonPayload.step)",
  "outcome": "EXTRACT(jsonPayload.outcome)", "reason": "EXTRACT(jsonPayload.reason)",
  "synthetic": "EXTRACT(jsonPayload.synthetic)" }

Shortened for the page; the file also describes each label.

Test traffic is tagged, and left out

The hourly synthetic sign-up sends the header X-Synthetic-Check: true. SyntheticTrafficFilter adds synthetic: "true" to every log line of that request, so it becomes a label too. Every chart and alert then filters on metric.label.synthetic!="true". Without that, test sign-ups would show up as customers, and would hide a real spike in Denmark's rejection rate.

The config can't drift from the code

Contract tests read infra/ on every build and fail if:

  • a chart or alert uses a label the metric doesn't have
  • it filters on an outcome, reason or market the app never writes
  • a chart or alert would count synthetic traffic
  • a chart is changed back to a line chart. The charts are bars on purpose: with one data point an hour, a line chart stays blank
  • the Denmark alert stops comparing REJECTED with SUBMITTED

Where to look: infra/MonitoringConfigContractTest.java

Two alerts, both by email

"Nordic Onboarding is down"

An uptime check calls /actuator/health every 5 minutes from Europe, the USA and Asia Pacific. It passes on a 2xx answer that contains "status":"UP". The alert fires when the check fails from 2 or more locations, so one bad network path doesn't wake anyone.

"Denmark: rejection spike"

Two conditions, and both must hold over the last 30 minutes:

  1. More than half of Denmark's submitted applications were rejected.
  2. At least 5 were submitted.

The second condition stops one rejected application out of one, at night, from counting as a spike. The email includes what to do next.

The address isn't in the repository. The repository is public, so the email address is passed to infra/apply.sh when it runs, never written to a file.

The incident loop, rehearsed

On 17 October 2026, the whole loop was run against production. The times are Swedish time.

17:19

A real Danish application, made by hand, is accepted.

17:21

Six Danish applications with an under-18 CPR number are sent with curl, skipping the browser. The server rejects all six: 422, ID_UNDER_AGE.

17:25

The "Denmark: rejection spike" alert opens and emails: 6 of 7 rejected, 86%, with 7 submitted.

By 18:05

The 30-minute window has moved past the rejections, so the alert closes by itself and sends a "recovered" email.

That evening

The kill switch: Actions → toggle market → SE. The run reports "Live markets changed from SE,DK to SE", and Denmark answers 404 while Sweden keeps working. Then toggle market → SE,DK, and Denmark answers again.

"Recovered" means the spike stopped, not that Denmark was fixed. A switched-off market gets no applications, so the alert closes by itself either way. So the order matters: Denmark is fixed first, the fix is released while Denmark stays off, and only then does a person switch it back on. That works because a release never changes MARKETS_ENABLED: releasing the fix can't switch Denmark on by itself.

Checks that run without anyone watching

The hourly synthetic sign-up

A scheduled GitHub workflow runs at 23 minutes past every hour. For each live market it does what a customer does: logs in, checks the demo ID number, and opens an account. If any market can't open one, the workflow fails and GitHub shows it.

It uses only the public URL, and its requests are tagged synthetic.

The kill switch

The "toggle market" workflow offers three choices: SE,DK, SE or DK. It sets MARKETS_ENABLED on Cloud Run, which starts a new revision from the same image, moves traffic to it, and then checks that each market is live or dark as asked.

It takes about a minute, because no code is built: it only changes a setting. It waits in the same queue as releases, so a release running at the same time can't undo it.

Monitoring as code

infra/ holds the metric, the dashboard, the uptime check and both alerts as JSON. infra/apply.sh PROJECT_ID ALERT_EMAIL creates or updates them, in the order they depend on each other, and is safe to run again:

  1. the log-based metric
  2. the dashboard, matched to the live one by its title
  3. the email channel, found by its address
  4. the uptime check, pointed at the live service
  5. the alert policies, linked to the channel and the check

The project's owner runs it by hand. CI's deployer is deliberately not allowed to change monitoring.

Design decisions

Why metrics from log lines, instead of a metrics library?
The events are already written as structured logs, so Cloud Logging can count them with no extra library, agent or endpoint. The metric's definition lives in the repository like everything else.
Why a rejection rate with a minimum count, not a plain count?
A count grows with traffic, so it would fire on a busy, healthy day. A rate alone would fire on one rejection out of one. Together they mean "most of a real number of applications failed".
Why is switching a market off a manual step, not automatic?
Many rejections can be a bug, or just people typing the wrong number. A person decides, and the alert email says how. Switching a healthy market off by mistake would cost real customers.
Why mask ID numbers by pattern, when events never contain them?
Defence in depth. A future log line, an exception message or a library could include one by accident. The pattern catches it in every line.
Why test traffic in production at all?
It proves the real thing works, every hour, including the eID step and both markets. Tagging keeps it out of the numbers that describe customers.
Limits. Alerts go by email only, the service runs in one region, and Cloud Logging keeps logs for its default 30 days.
